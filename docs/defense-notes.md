# 答辩要点

> 用途：自述稿 + 老师可能追问的问题与参考回答。回答都基于本项目**真实实现**，不要背结论，对着代码讲更稳。

## 一、1 分钟项目自述

> 我的毕业设计是一个面向中小零售门店的进销存与库存预警管理系统。
> 后端用 Spring Boot 3，管理端用 Vue 3，另外用 uni-app 做了一套**微信小程序**给店员日常使用。
>
> 它要解决的是小门店真实遇到的问题：便利店、文具店这类门店靠手工记账，容易出现
> **库存对不上、快过期的货没及时处理、补货靠拍脑袋**这三种情况。
>
> 系统围绕「进货 → 卖货 → 盘点 → 预警 → 补货」这条闭环做了 18 张表、13 个业务模块，
> 覆盖商品供应商管理、采购入库、销售出库、退货、批次与保质期、盘点、五类预警、四类统计报表。
>
> 技术上我重点做了三件事：
> **第一，库存扣减的一致性**，我实现了数据库乐观锁和 Redis+Lua 两套方案，并且内置压测接口可以直接对比；
> **第二，批次与保质期管理**，出库按「先到期先出」，退货原路退回原批次；
> **第三，结合 Spring AI 做了智能补货和库存问答**，但补货数量是本地算法算的，AI 只负责解释，所以断网也不会给出假数据。
>
> 前后端一共 42 项端到端冒烟测试全部通过。

## 二、五个核心亮点（按含金量排序）

### 亮点 1：库存扣减一致性 —— 两套方案可切换、可压测对比

**怎么讲**：

> 并发扣库存最典型的 bug 是「丢失更新」，导致超卖。朴素写法是先 `SELECT` 查库存、业务代码判断、
> 再 `UPDATE`，两个请求都读到 100，各扣 5，最后库存变成 95 而不是 90。
>
> 我做了两套方案，用配置切换：
>
> 第一套是数据库乐观锁，`UPDATE stock SET quantity = quantity - #{need}, version = version + 1
> WHERE id = ? AND version = ? AND quantity >= #{need}`。把「库存够不够」的判断塞进 UPDATE 的 WHERE 里，
> 影响行数为 0 就说明被并发改了或者库存不够，业务层重试，最多 3 次。
>
> 这里有个坑我踩过：MySQL 默认隔离级别是 `REPEATABLE_READ`，事务内的快照读会一直读到旧的 version，
> 导致重试时读到的版本号永远不变，乐观锁重试**永远失败**。所以我把事务隔离级别显式改成了 `READ_COMMITTED`。
>
> 第二套是 Redis + Lua，把判断和扣减写在同一个 Lua 脚本里，Redis 单线程执行保证原子性，
> 把竞争挡在数据库之前，再由事务落库，缓存在事务提交后同步。
>
> 为了证明这两套方案真的有效，我写了压测接口，用线程池加 `CountDownLatch` 制造瞬时并发，
> 返回 QPS 和一致性结论。一致性判定是「成功次数 × 每次扣减量 = 实际库存减少量」。
> 现场可以两种模式各跑一遍对比。

**可能被追问**：

| 问题 | 回答 |
|---|---|
| 为什么用乐观锁不用悲观锁？ | 门店场景读多写少，悲观锁（`SELECT ... FOR UPDATE`）会持有行锁到事务结束，并发扣同一商品时全部排队，吞吐低；乐观锁冲突才重试，无冲突时零额外开销。而且我们的冲突率很低，重试成本可以接受。 |
| 重试 3 次还失败呢？ | 返回业务码 4002「库存被并发修改，请重试」，让用户重新提交。这是可预期的失败，不应该无限重试占着连接。 |
| 乐观锁会不会死循环？ | 不会，重试次数是硬上限（`app.stock.max-retry`），超了就返回失败。 |
| Redis 方案如果 Redis 挂了怎么办？ | 缓存未命中时 Lua 脚本返回 -1，代码会回落到数据库扣减，也就是退化成方案 A，不会因为缓存故障导致业务中断。 |
| 缓存和数据库会不会不一致？ | 缓存在**事务提交后**才同步，避免事务回滚造成脏缓存；且缓存一律带 TTL 兜底。 |
| 为什么 Lua 里要先判断 `cur < 0`？ | 区分「缓存没预热」和「库存不足」两种情况，前者要回落数据库，后者要直接拒绝。 |

### 亮点 2：批次与保质期 —— FEFO 先到期先出

**怎么讲**：

> 零售的货是一批一批进来的，同一商品不同批次的成本价和到期日都不一样，所以我把库存拆成了两层：
> `stock` 表是商品维度的汇总，`stock_batch` 表是批次明细。
>
> 入库时按「生产日期 + 商品保质期天数」自动推算到期日并生成批次号。
> 出库的时候按 FEFO 排序 —— `ORDER BY expire_date ASC`，同时用
> `expire_date >= CURDATE()` 把已经过期的批次直接排除掉，保证过期商品不会被卖出去。
> 一个销售明细如果需要跨批次扣减，会记录每一段的扣减结果。
>
> 退货的时候我做的是**原路退回原批次**，而不是新建一个批次。因为新建批次会让批次账和实物对不上，
> 也无法反映真实的可售库存。

**可能被追问**：

| 问题 | 回答 |
|---|---|
| 保质期为 0（比如文具）怎么处理？ | `shelf_life_days = 0` 表示不管理效期，`expire_date` 存 NULL。排序时 `ORDER BY expire_date IS NULL, expire_date ASC` 把 NULL 排在最后，MySQL 里 NULL 默认排最前，不显式处理会优先出不管理的货。 |
| 临期的定义是多少天？ | 距到期 30 天内，配置项 `app.alert.near-expiry-days`，可以按品类调整。 |
| 出库成本怎么算？ | 移动加权平均。入库时重算 `avg_cost = (原库存 × 原成本 + 本次入库量 × 进价) / (原库存 + 本次入库量)`，保留 4 位小数；出库时用当时的 `avg_cost` 计价。 |
| 为什么用移动加权平均而不是先进先出计价？ | 先进先出需要严格按批次结转成本，实现复杂且对门店没多少收益；移动加权平均是会计上允许的简化方法，结果差异小、计算稳定。**但批次追溯用的是 FEFO**，两者不矛盾：一个是实物出库规则，一个是成本计价方法。 |

### 亮点 3：盘点差异可追溯

**怎么讲**：

> 盘点的难点不是录入实盘数，而是**差异怎么解释**。
>
> 关键决策是：提交盘点时以「当前库存」为准调平，而不是用建账时的快照。
> 因为实际场景里，建账（上午）和提交（下午）之间往往还在正常卖货。
> 如果按快照算差异，中间卖掉的货就会被算成盘亏。
>
> 所以我的逻辑是 `差异 = 实盘数 − 当前库存`，正数走盘盈入库，负数走盘亏出库。
> 同时保留账面数快照和提交时的实际差异，并且每一笔盘盈盘亏都写库存流水，
> 流水的 `bizNo` 写入盘点单号，所以打开「库存流水」按盘点单号一筛，这次盘点产生了哪些调整一目了然。
>
> 另外盘点明细里保留了「账面数 → 实盘数 → 差异 → 差异原因」，原因由录入人手工填，比如「货架串位」「破损报废」。

**可能被追问**：

| 问题 | 回答 |
|---|---|
| 盘点期间允许继续开单吗？ | 允许。这是我刻意的设计，就是为了避免把正常销售误判成盘亏。代价是实盘数必须是盘点那一刻的真实数字，一般盘点会短暂停止收银。 |
| 已完成的盘点能改吗？ | 不能，只能重新建单修正。盘点是财务性质的记录，改历史会让责任无法追溯。 |
| 盘点会锁库存吗？ | 不会。走的是同一套库存引擎，有版本号保护，并发下也不会算错。 |

### 亮点 4：Spring AI 智能补货与库存问答

**怎么讲**：

> 我用 Spring AI 做了两个功能，但设计原则是「AI 是增强，不是依赖」。
>
> **第一个是智能补货建议**。补货数量由本地算法算，公式是：
> 日均销量取移动平均 → 安全库存 = Z × 日销量标准差 × √到货周期（Z 取 1.65 对应 95% 服务水平）→
> 补货点 = 日均销量 × 到货周期 + 安全库存 → 建议补货量 = 补货点 × 2 − 当前库存。
> 接口会把日均销量、安全库存、补货点、可支撑天数这些中间量全部返回，所以每一个数字都能解释来源。
> AI 只负责把这些数字写成一段人话。没配 API Key 的时候，这部分降级成本地规则文案，功能不中断。
>
> **第二个是库存智能问答**，用的是 Function Calling。我把查询库存、查临期批次、查低库存商品
> 这些能力注册成工具，模型自己决定调哪个工具，答案严格基于查询结果。
> 接口会返回 `toolsUsed`，能看出它这次实际用了哪些工具，这样可以验证答案不是模型编的。
>
> 接入方式上我用的是 OpenAI 兼容协议接阿里云百炼，好处是换模型只改一个 `model` 配置，代码零改动。
> 流式输出用的是 Reactor 的 `Flux`，不是 `SseEmitter`，因为 Spring AI 的流本身就是 Flux，
> 直接透传少一层转换，也不会丢掉背压信号。

**可能被追问**：

| 问题 | 回答 |
|---|---|
| 模型会不会编数据？ | 会，所以数量从来不让模型算。补货量是本地算法的结果，问答走 Function Calling 强制查库，答案基于工具返回的真实数据。 |
| 安全库存为什么乘 Z 值？ | 这是库存管理里的标准做法。Z 是正态分布的分位数，Z=1.65 对应 95% 的服务水平，意思是「有 95% 的把握不断货」。σ × √L 是到货周期内的需求标准差，因为需求在到货周期内累积，方差按时间开方放大。 |
| 到货周期怎么来的？ | 目前是按供应商维护的固定值（默认 3 天）。更严谨的做法是按历史采购单的「下单到入库」时长算实际均值，这是我下一步想改进的点。 |
| AI 不可用时页面显示什么？ | 返回 `degraded: true`，前端会有明显提示「AI 服务暂不可用，以上为本地规则生成的兜底说明」，不会假装正常。 |
| 为什么不直接 `RestTemplate` 调大模型接口？ | 手写要自己处理消息结构、流式解析、工具调用协议，代码量和出错面都大；Spring AI 把这些封装好了，而且换模型不用改代码。 |

### 亮点 5：认证方案 —— 令牌不落 localStorage

**怎么讲**：

> 认证这块我做了几个刻意的选择。
>
> Access Token 是 JWT，30 分钟过期，**只存在前端内存里**，不放 localStorage。
> 因为 localStorage 能被任意 JS 读到，一旦 XSS 就等于泄漏长期凭据。
> 放内存的代价是刷新页面会丢，所以配了一个刷新令牌放在 httpOnly Cookie 里，7 天有效，刷新页面时用它换新的。
>
> 刷新令牌我做了服务端落库，不是纯 JWT。因为纯 JWT 没法主动吊销 ——
> 用户点了退出，旧令牌照样有效到过期。落库之后退出即删记录，令牌立刻失效。
> 而且每次刷新都会换发新令牌并删除旧的，也就是令牌轮转，旧令牌被重放会被直接拒绝。
>
> 前端这边，axios 拦截器遇到 401 会自动调刷新接口再重放原请求。
> 这里有个细节：刷新请求用的是「单例 Promise」，因为页面上可能同时发好几个请求，
> 如果不做单例就会同时打出多个刷新请求。而刷新接口本身失败时会有明显的错误提示并跳登录页。

**可能被追问**：

| 问题 | 回答 |
|---|---|
| JWT 和 Session 有什么区别？为什么选 JWT？ | Session 把状态放在服务端，多实例部署要额外做共享（比如存 Redis）；JWT 无状态，服务端不存会话，横向扩展方便。代价是没法主动吊销，所以我用「短时效 access token + 落库可吊销的 refresh token」来补这个短板。 |
| Cookie 不怕 CSRF 吗？ | 刷新令牌的 Cookie 设置了 `SameSite=Lax`，跨站请求不会带上它；同时刷新接口只接受带 Cookie 的 POST，不做数据修改，风险面很小。真正改数据的接口用的是 Authorization 头里的 access token，不受 CSRF 影响。 |
| 令牌放内存，用户刷新页面体验不是断了吗？ | 不会，路由守卫里会先用刷新令牌静默换一次 access token，用户无感知。 |
| 密码怎么存的？ | BCrypt 哈希，不存明文。种子数据里的密码也是哈希值。 |

### 亮点 6：同一套认证体系同时服务 PC 端与微信小程序

**怎么讲**：

> 除了 PC 管理端，我还用 uni-app 做了一套微信小程序给店员用。
> 理由是门店里店员是拿着手机在货架之间走动的，扫码查货、随手开单比跑到电脑前方便得多。
>
> 这里遇到的第一个问题是认证。PC 端的刷新令牌放在 httpOnly Cookie 里 —— 那是浏览器的方案，
> JS 读不到，XSS 也偷不走。但小程序没有浏览器那套 Cookie 语义，硬塞 Cookie 会出现
> 「真机正常、开发者工具异常」这类很难查的问题。
>
> 我的做法不是另起一套认证，而是**让同一套逻辑支持两种令牌载体**：
> 登录时多传一个 `client: "MINI"`，后端就把刷新令牌放在响应体里返回，由小程序存进本地缓存；
> 不传就还是走 Cookie。校验、轮转、吊销这些真正的业务逻辑**两端完全共用**，不存在两份实现，
> 而且 PC 端行为一点没变 —— 这一点我用冒烟测试里「Web 模式」的用例专门守住了。
>
> 第二个问题是令牌存哪。access token 依然**只存内存**；小程序冷启动内存一定是空的，
> 所以启动时用本地留存的 refreshToken 静默换一张新的，用户完全无感，失败才回登录页。
>
> 移动端还按场景做了几个针对性设计：扫码查货把「输名称 → 搜索 → 翻页」压缩成扫一下；
> 开单时库存不足的错误留在页面上而不是一闪而过的 toast，店员能对着提示直接改数量重试。

**可能被追问**：

| 问题 | 回答 |
|---|---|
| 为什么不直接用微信授权登录（`wx.login`）？ | 可以做，但那是**身份认证**，回答「你是谁」；这个系统还需要**权限**——店员和店长能看的、能做的都不一样。所以账号密码 + RBAC 更直接。将来若做顾客端，再叠加 openid 绑定即可。 |
| 小程序存 refreshToken 安全吗？ | 比浏览器 localStorage 安全：小程序缓存是沙箱隔离的，其他小程序和网页读不到。而且刷新令牌落库可吊销、每次刷新轮转，泄露一个用一次就失效。access token 依旧只存内存。 |
| 两端代码怎么复用的？ | 复用的是**后端**。前端是两套：PC 端 Element Plus + ECharts；小程序没有 DOM，axios 和 ECharts 都跑不起来，改用 `uni.request` 封装（含 401 单例刷新重放）和自己的 view 拼柱状图。 |
| 小程序上线要备案域名吗？ | 正式发布需要 HTTPS + 已备案域名。开发阶段在开发者工具里勾上「不校验合法域名」就能直连本地 http；真机预览走局域网 IP，答辩演示完全够用。 |

## 三、其他常见问题速查

| 问题 | 回答要点 |
|---|---|
| **系统有多少张表？** | 18 张。系统 2 张、基础资料 3 张、采购 2 张、销售 2 张、退货 2 张、库存 7 张、AI 1 张。 |
| **数据量多大？** | 种子数据 30 个商品、6 家供应商、54 张采购单、90 张销售单、149 个批次、2908 条库存流水，销售数据覆盖 90 天。 |
| **怎么做分页的？** | MyBatis-Plus 分页插件，统一返回 `{records, total, current, size, pages}`；每页最大 500 条，防止恶意拉全库。 |
| **索引怎么建的？** | 唯一索引建在业务编码上（商品编码、单号、批次号）；查询索引按实际 WHERE 条件建（`stock.product_id`、`stock_record.biz_no`、`stock_batch.expire_date` 等）。 |
| **参数校验做在哪一层？** | 在 Controller 边界用 `@Valid` / `@Validated`，配合全局异常处理器统一转成中文提示。数据库约束作为最后一道防线（唯一索引冲突会转成友好的「数据重复」提示，不暴露表结构）。 |
| **接口返回格式统一吗？** | 统一 `{code, message, data, requestId, timestamp}`。业务失败也返回 HTTP 200 + 业务码，前端只看 `code`，这样 4xx 不会和网关的错误混在一起。 |
| **日志怎么做的？** | 结构化日志，每个请求生成 `requestId` 同时写进日志和响应头 `X-Request-Id`，排查问题时可以按 requestId 串起整条链路。密码和令牌不记录。 |
| **为什么不把 AI 调用放在请求线程里？** | 慢任务确实不该占请求线程，但补货分析和问答本身就是用户点了才触发的同步交互，用户就在等结果，所以是同步 + 超时（3 分钟）而不是异步任务。如果要做批量分析，会走独立进程。 |
| **前端怎么处理接口错误的？** | 拦截器统一解包，把后端 `message` 直接展示给用户；4xx 不重试、5xx 最多重试 3 次；网络断开显示「请确认后端服务已启动」而不是白屏。 |
| **系统的不足？** | 三点：① 到货周期目前是固定配置，应该按历史采购单算实际值；② 补货算法是移动平均，遇到促销、季节波动会滞后，可以考虑加指数平滑；③ 没有做单元测试，目前是 42 项端到端冒烟测试覆盖主流程，自动化测试是下一步要补的。 |
| **如果要支持多家门店怎么做？** | 加 `store_id` 字段做数据隔离，`stock` 和 `stock_batch` 的唯一键加上门店维度，报表按门店汇总。架构上不用大改，因为业务逻辑都集中在 Service 层。 |

## 四、演示流程建议（8 分钟）

按「发现问题 → 解决问题」的顺序演，比按菜单顺序演更有说服力。

| 顺序 | 操作 | 想说明什么 |
|---|---|---|
| 1 | 登录（admin），看**工作台** | 系统全貌：今日/本月销售、库存成本、待办事项、销售趋势 |
| 2 | 打开**库存预警**，点「立即扫描」 | 五类预警一次扫出来；再点一次扫描，数量不变 → **幂等**，不会重复堆数据 |
| 3 | 打开**批次与保质期**，筛「仅看临期 / 仅看已过期」 | 批次粒度管理，剩余天数和效期状态 |
| 4 | **新建采购单 → 入库**，回商品页看库存 +N，去**库存流水**看记录 | 采购入库生成批次、增库存、写流水，一步不落 |
| 5 | **新建销售单**，故意填一个超过库存的数量 | 返回明确的中文提示「商品【xx】库存不足，当前 691，需要 999999」 → **防超卖** |
| 6 | 正常开一单，再**作废**它，看库存回滚 | 出库扣批次、作废原路退回 |
| 7 | **盘点**：新建只选 1 个商品 → 实盘数填少 3 个 → 提交 | 差异自动生成盘亏流水，去流水页按盘点单号筛选 → **差异可追溯** |
| 8 | **并发扣减压测**：DB 模式跑一次，REDIS 模式跑一次 | 对比 QPS 和一致性结论，这是压轴的演示 |
| 9 | **AI 智能助手**：看补货建议表 → 点「AI 分析」看流式输出 → 切到「库存智能问答」问「哪些商品快过期了」 | 数量本地算、文字 AI 写；问答会显示调用了哪些工具，证明答案基于真实数据 |

## 五、移动端演示（可选，2 分钟）

移动端展示的**不是**同一套界面的缩小版，而是针对「店员拿着手机在货架之间走动」
这个场景重新设计的一套操作路径。

| 顺序 | 操作 | 想说明什么 |
|---|---|---|
| 1 | 登录后**关掉小程序再重新打开**，不再要求输密码 | 冷启动用本地 refreshToken 静默换 access token，店员每天上班不用重复登录 |
| 2 | 点「扫码查货」，扫任意商品条码 | 把「输名称 → 搜索 → 翻页」压缩成扫一下，这是移动端独有的价值 |
| 3 | 进「销售开单」，把某个商品的数量加到超过库存 | **库存不足的提示留在页面上**，不是弹个一闪而过的 toast，店员能对着提示改数量重试 |
| 4 | 提交成功后看销售单详情 | 开单即出库，明细里能看到实际扣的是哪个批次 |
| 5 | 进「AI 助手」切到智能问答，问「哪些商品快过期了」 | 同一个后端、同一个模型，答案是真实数据 |

> 若被问「小程序和 PC 端是不是同一套代码」：
> **前端是两套**（小程序没有 DOM，axios 与 ECharts 都用不了，改用 `uni.request` 和自己的 view 拼图表），
> **后端是同一套**，认证也是同一套逻辑支持两种令牌载体。
